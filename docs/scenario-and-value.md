# 场景与价值分析

> 对应赛道 B 评分项「场景价值与痛点判断」（20 分）。
> 本文回答四个问题：谁用、痛在哪、现在怎么解决、Sextant 到底多做了什么。

---

## 1. 目标用户

**主用户：需要定期追踪一个研究方向的研究生和初级研究者。**

典型画像：

- 每周或每两周要向组会、开题、项目立项汇报一次「这个方向最近有什么新工作」。
- 同时使用 arXiv、Google Scholar、PubMed 或所在领域的数据库，英文阅读没问题，但筛选和整理耗时。
- 没有专职情报人员，也没有预算购买 Scopus、Web of Science 这类商业数据库。
- 需要把「为什么选这几篇」讲清楚，而不是只丢一个链接列表。

**次用户：**

- 技术选型负责人/研发工程师：需要快速判断某个技术方向有哪些代表性工作、各自解决什么问题。
- Agent 开发者：不关心界面，希望把「检索 + 排序 + 证据目录」当成一个 MCP 工具，接进自己的 Agent 工作流。

**明确不是目标用户：**

- 需要全文精读、论文复现、实验管理的研究者——Sextant 只做到摘要级证据，不做 PDF 管理和实验跟踪。
- 需要中文文献、专利、行业报告的用户——当前来源以英文学术元数据为主。

---

## 2. 真实痛点

以「周一要汇报 Agent Memory 方向近期进展」为例，现在通常这样做：

| 环节 | 现在怎么做 | 实际代价 |
|---|---|---|
| 发现 | 在 OpenAlex / arXiv / Google Scholar 之间反复切换，换关键词搜 | 4–6 个入口；同一个工作在不同库里重复出现；预印本和正式版分不清 |
| 初筛 | 逐条看标题和摘要，判断是否相关 | 100 条左右要读 1–2 小时，且高度依赖个人判断 |
| 整理 | 把选中的论文粘进文档，补作者、年份、链接 | 机械劳动；链接失效或漏填很常见 |
| 汇报 | 再写一段「本方向趋势」 | 时间都花在搬运上，真正分析的时间被压缩 |
| 复现 | 下周想再看一次，或同事问「你当时怎么筛的」 | 搜索词、筛选理由、结果都没有留下，只能重来 |

核心痛点不是「搜不到」，而是**从搜到到可用之间的那段重复劳动不可见、不可复用、不可解释**。

---

## 3. 现有解决方式对比

| 方式 | 能做什么 | 缺什么 |
|---|---|---|
| Google Scholar 订阅/快讯 | 覆盖面广，能按关键词推送新论文 | 不跨库去重；不解释排序；不产出结构化证据目录；无法限定一次运行的范围并复现 |
| Connected Papers | 以一篇种子论文为中心画引用关系图 | 适合「顺藤摸瓜」，不适合「按主题持续追踪」；不处理多源去重和时间窗 |
| Zotero / EndNote | 管理已经收集到的文献 | 只负责「管」，不负责「发现、去重、排序」 |
| 人工 RSS + 表格 | 完全可控 | 全靠人力；来源一多就维护不动 |
| 通用聊天助手 | 一句话生成一段领域综述 | 来源不可核验；无法保证时间窗；每次结果不同；无法逐条回溯到论文 |
| **Sextant** | 一次输入主题，完成多源检索、去重、可解释排序、证据目录，按需生成中英双语报告 | 摘要级证据；不覆盖中文文献和专利；不做全文精读 |

Sextant 的定位不是「又一个文献搜索框」，而是**把发现到交付之间的链路做成有状态、可审计的产物**。

## 4. Agent 带来的增量

### 4.1 任务拆解，而不是一次模型调用

一次运行被拆成六个有明确输入输出的阶段：

```
plan → retrieve → normalize → enrich → rank → render
```

- `plan`：选择来源、生成每个来源的检索式；模型可用时扩充同义词，不可用时退回规则。
- `retrieve`：每个来源一个线程并行检索，同源查询串行以尊重限流。
- `normalize`：DOI / 标题指纹去重，合并多源命中，摘要不合格的记录进入待核实区。
- `enrich`（可选）：中文标题、中文摘要、一句话结论、研究方向。
- `rank`：关键词覆盖 40 + 标题命中 10 + 引用量 20 + 时效性 20 + 跨源印证 5 + 质量 5。
- `render`：生成自包含的证据目录，支持来源、年份、类型筛选和中英摘要切换。

报告不是第七段，而是目录生成后的**按需独立任务**：它有自己的 `run_id`、日志、SSE 流和失败边界。目录先可用，报告慢慢生成，二者互不阻塞。

### 4.2 工具调用，而不是黑箱

同一套 pipeline 通过 MCP 暴露为工具：`create_topic`、`run_topic`、`generate_report`、`get_run_status`、`search_papers`、`score_records` 等。Web 控制台和 MCP Agent 是两个入口，不是两套系统。

这意味着 Sextant 可以被更大的 Agent 工作流调用，而不是把用户锁在一个网页里。

### 4.3 状态与恢复，而不是一次性脚本

- 每个阶段的输入输出都落在主题工作区，阶段可独立重入，失败不会留下半截状态被下一阶段误用；控制台「重跑」重新执行整条链路，上一轮日志和 `runs.json` 记录保留，`catalog.html` 会被本轮覆盖。
- 每次运行有独立的 `logs/<run_id>.jsonl`，记录 `seq / ts / stage / status / duration_ms / data`。
- 同一主题同一时刻只允许一个任务（检索或报告），避免两路写入同一目录。
- 检索失败不会破坏已有目录；报告失败保留旧报告，不会把可用产物删掉。

### 4.4 增量收益，尽量量化

以一次真实运行为例（主题 `Agent Memory Systems Acceptance`，4 个来源，`deepseek-flash`）：

| 指标 | 人工方式（估算） | Sextant（实测） |
|---|---|---|
| 原始记录 | 取决于搜多少 | 120 条 |
| 去重后 | 人工很难逐条比对 | 102 条 |
| 进入精读的范围 | 100 条左右 | Top 20（按可解释分数） |
| 初筛耗时 | 100 条 × 40–60 秒 ≈ 70–100 分钟 | 检索 + 中文增强约 128 秒 |
| 汇报材料 | 再花 30–60 分钟整理 | 目录即时可用；报告约 1–2 分钟 |
| 可追溯性 | 链接和筛选理由容易丢 | 每条记录带来源、日期、引用数、分数构成 |
| 复现性 | 搜索词和结果通常不留 | 查询计划、日志、产物全部落盘，可重跑 |

> 人工耗时是按「每条摘要粗读 40–60 秒」的保守估算，不是用户实验数据；Sextant 的数字来自 `run_summary.json` 和运行日志。两者口径不同：Sextant 的 128 秒包含检索、去重、中文增强和目录渲染，不只是初筛。这里只用于说明数量级差异。

### 4.5 为什么不是「聊天套壳」

- **证据在前，语言在后**：目录由确定性的检索、去重、排序产生；不配置模型时整条链路照常可用，只是没有中文摘要。
- **模型只做增强**：查询扩展、中文翻译/归类、报告写作。模型失败时降级，不阻断主流程。
- **每个结论可回指**：报告里的论文卡片必须落到某个分析小节；渲染器会校验「每张卡都有归属」，否则拒绝产出。
- **产物可复现**：同一主题重跑会留下新的 `run_id` 和日志，`runs.json` 保留历史运行记录；目录文件按最新一次运行覆盖。

## 5. 价值验证

### 5.1 已完成的验证

- **真实主题走查**：`Agent Memory Systems Acceptance`、`DeepSeek`、`RAG` 等主题都跑过完整链路；以 `Agent Memory Systems Acceptance` 为例，4 个来源、120 条原始记录、102 条去重后记录、40 条中文增强。
- **降级验证**：不配置模型时完整跑通，目录保留英文原文；模型批次失败时只损失该批 10 条，其余批次正常写回。
- **失败隔离验证**：PubMed 证书校验失败时该来源记为 `warning`，其余来源结果照常产出目录。
- **报告独立性验证**：报告任务运行期间目录始终可访问；重复点击返回 409；报告失败不删除旧报告。原始日志摘录见 [evidence.md](evidence.md)。

### 5.2 还没有做的验证

- **没有正式用户研究**：目前是作者自用 + 单个真实主题走查，没有 3–5 名目标用户的对照试用。
- **没有命中率标注集**：Top 20 的相关性还没有人工标注后的 precision/recall 数字。
- **没有和商业数据库对比**：未与 Scopus、Web of Science 做覆盖率和排序质量对比。

这三项是下一步最值得补的价值证据，也是答辩时应该主动说明的边界。

### 5.3 成功标准

| 维度 | 标准 | 当前状态 |
|---|---|---|
| 覆盖 | 一个细分主题至少 4 个来源、100 条原始记录 | 达成（120 条） |
| 去重 | 重复记录合并，保留跨源命中数 | 达成（120 → 102） |
| 可追溯 | 每条记录有来源和可点击链接 | 达成 |
| 延迟 | 无模型 < 6 秒；含中文增强 < 3 分钟；报告 < 3 分钟 | 达成（1.2–5.6 秒 / 约 128 秒 / 80–135 秒） |
| 可复现 | 查询计划、日志、产物全部落盘，可重跑 | 达成 |
| 排序质量 | Top 20 人工抽检相关率 ≥ 70% | **待验证** |

## 6. 边界与非目标

- **摘要级证据**：不做全文解析、不做实验复现、不做引用上下文分析。
- **英文学术元数据为主**：不覆盖中文期刊、专利、行业报告。
- **面向个人/小团队**：当前版本按需运行，不追求高并发。
- **不自动发布**：报告和目录都落在本地工作区，是否对外分享由用户决定。

这些边界不是能力不足的借口，而是当前阶段刻意收缩范围：先把「发现 → 去重 → 排序 → 交付」这条主链路做扎实，再扩全文和向量召回。
