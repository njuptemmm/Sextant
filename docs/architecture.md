# 系统架构设计

## 1. 设计目标与约束

| 目标 | 约束 | 设计结果 |
|---|---|---|
| 评委能在 5 分钟内复现 | 不能依赖云账号、数据库、GPU | 单进程 FastAPI + 磁盘工作区 + `docker compose up` |
| 一次运行 30–90 秒，需要实时反馈 | 不能用轮询把界面做糊 | SSE 推送阶段事件，事件同时落 JSONL |
| 外部学术接口不稳定 | 单源失败不能拖垮整次运行 | 每源独立线程 + 独立失败域 + 降级 |
| 模型是增强项 | 没有 key 也必须能跑 | LLM 调用失败返回空结果，链路继续 |
| 结果要能用于答辩追问 | 排序必须可解释 | 每个分数项写入 `ranking_reasons` |

**明确不做**：多租户、权限体系、分布式任务队列、向量数据库。这些会显著增加部署复杂度，但对当前「单用户、单机、按需运行」的负载没有收益。架构预留了替换点（见第 6 节）。

### 依赖方向

```
web → api → pipeline → engine
                 ↘ workspace（仅文件 I/O）
```

- `engine` 不 import `pipeline` / `api`，可以单独用于脚本或测试。
- `pipeline` 不直接发 HTTP：所有外部请求都经过 `engine.sources`，保证限流与重试只有一处实现。
- `api` 不解析外部响应体：它只处理已归一化的记录。
- `web` 不含业务逻辑：只渲染事件和调用 REST。

## 3. 关键设计决策

### 3.1 磁盘工作区，而不是数据库

**选择**：每个主题一个目录，所有中间产物都是 JSON / JSONL / HTML。

**理由**：
- 评委可以直接打开目录查看证据链，不需要连数据库。
- 运行失败后，文件就是现场：`queries.json` 说明系统想查什么，`02_raw/` 说明实际拿到了什么，`ranked_articles.jsonl` 说明为什么这样排序。
- 迁移成本低：将来接对象存储只需要替换 `workspace.py` 的读写函数。

**代价**：并发写同一主题需要互斥。当前用「一主题每类任务一个活跃任务」的注册表规避，而不是文件锁。

### 3.2 进程内线程池，而不是 Celery

**选择**：`JobRegistry` 为每个任务起一个守护线程。同一主题同时只允许一个检索任务和一个报告任务，两者互斥（报告依赖检索产出的排序结果）。

**理由**：部署零依赖；任务时长在分钟级以内，线程足够；SSE 可以直接从内存事件总线广播。

**代价**：进程重启会丢失运行中的任务（已完成的结果仍在磁盘）。扩展路径见第 6 节。

### 3.3 报告是独立任务，不是第 7 段

**选择**：检索链路在 `render` 结束；报告由 `POST /api/topics/{id}/report` 触发，拥有独立的 `run_id`、JSONL 日志和 SSE 流。

**理由**：
- 报告需要 LLM 和多次往返（Top 20 实测 79–82 秒），而目录在几百毫秒内就绪。把报告塞进 pipeline 会让“目录已可用”这个事实被拖到最后，用户看不到已经能用的产物。
- 报告是可选消费行为，不是检索结果的一部分；用户可能只想看目录。
- 独立任务意味着失败域独立：报告失败不影响目录，旧报告在重试失败时也会保留。

**约束**：报告任务不写入 `runs.json`（否则会伪装成一次新的检索，污染 `last_run` 与主题列表）。它只通过 job registry 和 `logs/<report_run_id>.jsonl` 暴露状态；重跑检索会删除旧报告，因为旧报告描述的是旧排序集。

### 3.4 SSE，而不是 WebSocket

**选择**：`text/event-stream`，服务端按 `seq` 去重，带心跳注释行。

**理由**：单向推送足够；SSE 走普通 HTTP，反向代理配置简单；断线后浏览器自动重连，服务端先回放历史再续推实时事件。

**代价**：不能从客户端发消息。当前不需要。

### 3.5 分层单体，而不是微服务

见 README 第 4 节。核心判断：当前瓶颈是外部接口延迟，不是服务间耦合；拆分只会增加部署与排障成本。

### 3.6 可解释排序，而不是黑箱相关性

**选择**：六个可枚举的分数项，权重固定并写入记录。

**理由**：答辩时每个名次都能回答「为什么排在前面」；没有模型也能工作；后续加入向量召回时，可以把语义分作为第七项，而不是替换整个排序。

## 4. 负载、状态与故障恢复

| 维度 | 当前设计 | 依据 |
|---|---|---|
| 负载 | 单机、按需运行，峰值 1–3 并发主题 | 目标用户是个人研究者 |
| 状态 | 全部在磁盘；内存只有运行注册表与事件订阅者 | 进程崩溃不丢已完成结果 |
| 扩缩容 | 业务状态在磁盘；进程内只有任务注册表与事件订阅者 | 多副本需要共享卷 + 外置注册表/事件总线 |
| 故障恢复 | 单源失败隔离；阶段失败写日志并保留中间产物；重跑复用主题目录 | 见 `docs/error-handling.md` |
| 超时 | 外部请求 30 秒、重试 2 次；模型 45 秒 | 学术接口典型 P99 在 5 秒内，30 秒留足余量 |
| 限流 | 每源一个 `RateLimit`，同源查询串行 | arXiv 要求 3 秒/请求 |

## 5. 部署拓扑

```
          ┌──────────────┐
  浏览器 ─┤  api :8000   ├── 工作区卷 ./workspace
          └──────┬───────┘
                 │ 共享卷
          ┌──────▼───────┐
  Agent ──┤  mcp :8001   ├── 同一个 pipeline
          └──────────────┘
```

- 两个容器使用同一镜像，只是启动命令不同。
- 工作区通过 volume 挂载，两个进程看到同一份主题目录。
- 公网部署时在 `api` 前加反向代理（TLS + 鉴权）；`mcp` 同理。

## 6. 演进路径

| 触发条件 | 改动点 | 不需要改的部分 |
|---|---|---|
| 多副本部署 | `JobRegistry` 换成 Redis 队列；SSE 换成 Redis Pub/Sub | pipeline、engine |
| 主题数量上千 | 工作区换对象存储；增加索引表 | engine 适配器 |
| 需要语义召回 | 在 `rank` 前增加 `embed` 阶段，写入 `semantic_score` | 现有评分项与渲染 |
| 需要全文精读 | 复用 `engine` 的文档解析能力，增加 `deep_read` 阶段 | plan / retrieve |
| 需要多租户 | API 层加租户隔离，工作区前缀加租户 ID | 内核逻辑 |
